# CueFlow v0.6.2 Anonymous Trial Operation 冻结设计

状态：已批准并实现于 `trial-operation` 分支；部署前仍须使用真实配置通过 readiness。

分支：trial-operation

基线：v0.6.1，提交 1934a98999c0cc6764f8be64e2c7e6565f8c50c6。

## 1. 目标

v0.6.2 是为期一个月的零收费、零注册、零登录公开试运营。它是资源保护层和
实验数据采集层，不是匿名账户系统、商业计费系统或专业反欺诈平台。

本版必须能够回答：

1. 有多少匿名 Cookie 访客到达；
2. 有多少访客真正运行任务；
3. 有多少访客跨日回来继续使用；
4. 每个任务和每分钟音频产生多少可计算 API 成本；
5. 任务成功率、耗时和主要失败原因；
6. 在普通误用、Worker 崩溃或 Provider 用量未知时，服务是否仍能限制可用性和财务风险。

## 2. 当前基线与兼容边界

- 当前产品版本为 v0.6.1。
- v0.6.1 的 AccountStore、手机号、密码和 Auth HTTP 契约保持不变。
- Trial 部署创建独立的 create_trial_app，不挂载 create_auth_app；已有认证源码不删除。
- TrialStore 独立于 AccountStore 和每个 Workspace 的 Core Registry。
- v0.6.2 不修改字幕算法、Artifact ID、Provider retry 语义或 Core 状态真实性。
- v0.6.2 一旦在 trial-operation 分支形成版本，不得在 main 上把同一版本号用于其他发布。

Core 已支持由调用方指定 Workspace 根目录。Trial 每个稳定 job_id 使用
TRIAL_WORK_ROOT/job_id 作为独立 Workspace；同一 job 的用户 retry/resume 在其仍可用时
复用该 Workspace。

Core 的本地执行区原本是可恢复状态，不是天然临时目录。由 Trial 适配层创建并拥有的
Workspace 才适用本设计的短生命周期；普通 CLI 或其他调用方 Workspace 不受影响。

## 3. 明确不做

- 注册、登录、支付、套餐和发票对账；
- Phone Reputation、匿名历史与正式 Account 绑定；
- Canvas、WebGL、字体、音频或硬件设备指纹；
- 验证码、代理或 VPN 检测；
- 机器学习 risk score、设备图谱和公网申诉；
- 跨 Run 媒体复用或全局文件去重；
- 任务队列、Redis、分布式 counter 或 Worker 调度平台；
- 完整 operator RBAC；
- Trial GC 状态机、artifact ownership table 或 bucket-wide sweep。

## 5. 匿名身份

### 5.1 Visitor Cookie

首次访问生成至少 128 位不可预测随机值。生产 Cookie 契约为：

~~~
Max-Age=365 days
Secure
HttpOnly
SameSite=Lax
Path=/
~~~

有效访问时滑动续期。Cookie 不复制到 localStorage。

visitor_id 是匿名历史访问凭据。清除浏览器数据、使用无痕模式、换浏览器或换设备后，
历史不可恢复。本版不提供邮箱、手机号或人工申诉找回；未来注册账户也不自动继承
匿名历史、IP 或 fingerprint 信号。

### 5.2 IP

服务端只保存：

~~~
ip_hmac = HMAC-SHA256(normalized_ip, TRIAL_IP_HMAC_SECRET)
~~~

不保存原始 IP。默认使用直接连接地址；只有请求确实来自部署配置中的可信反向代理时，
才读取其转发地址。HMAC secret 缺失或可信代理配置无效时 readiness 失败。

### 5.3 Coarse fingerprint

客户端仅提交：

- browser family 和 major version；
- OS family；
- language；
- timezone；
- screen class。

服务端规范化后以独立 secret 计算 HMAC，只保存摘要。fingerprint 不是绝对身份，不单独
触发永久封禁；它只用于观察 Cookie 轮换趋势、辅助人工判断和实验统计。

## 6. TrialStore

TrialStore 使用独立 SQLite，共五张表。新增 trial_stats 是因为在线峰值属于高频统计，
不能混入低频、append-only 的控制审计。

### 6.1 trial_visitors

~~~
visitor_id PRIMARY KEY
fingerprint_hmac NULL
fingerprint_observed_at NULL
first_seen_at
last_seen_at
first_job_at NULL
second_active_day_at NULL
active_day_count
status CHECK normal | blocked
~~~

### 6.2 trial_requests

每个用户发起的 create/retry/resume 动作一行；同一产品任务共享 job_id。

~~~
request_id PRIMARY KEY
job_id
visitor_id
action_kind CHECK create | retry | resume
ip_hmac NULL
fingerprint_hmac NULL
core_run_id NULL
execution_status
reject_reason NULL
created_at
started_at NULL
terminal_at NULL
last_alive_at NULL
interrupted_at NULL
audio_duration_ms NULL
processing_duration_ms NULL
provider_invocation_count
estimated_max_cost_micros
calculated_cost_micros NULL
estimated_unknown_cost_micros NULL
cost_status
budget_released_at NULL
source_object_json NULL
result_object_json NULL
result_published_at NULL
~~~

Workspace 路径由受验证的 job_id 和 TRIAL_WORK_ROOT 确定，不把任意文件系统路径作为
数据库控制输入。

### 6.3 trial_usage

每个 Core invocation 最多一行，以 invocation_id 幂等。

~~~
invocation_id PRIMARY KEY
request_id
operation
provider
resolved_model NULL
invocation_status
input_tokens NULL
output_tokens NULL
cached_tokens NULL
reasoning_tokens NULL
total_tokens NULL
usage_json NULL
usage_source
pricing_version NULL
calculated_cost_micros NULL
currency
cost_status
created_at
~~~

### 6.4 trial_control

仅保存低频、append-only 的 operator 控制变更：

~~~
control_revision PRIMARY KEY
action CHECK pause | resume | set_daily_budget_override | clear_daily_budget_override
old_value_json
new_value_json
reason
created_at
~~~

当前控制状态由部署默认值和最新适用 revision 派生。不得把 heartbeat、在线人数、
peak_online 或普通请求状态写成控制 revision。

### 6.5 trial_stats

单行当前统计状态：

~~~
stats_key PRIMARY KEY CHECK stats_key = global
peak_online
peak_online_at NULL
updated_at
~~~

只有新峰值出现时才更新该行，不产生控制审计记录。其他统计优先由 visitors、requests
和 usage 查询聚合，不复制长期 counter。

### 6.6 保留与脱敏

- visitor、request、result ref 和 usage 不设自动过期，以支持长期历史和实验复盘；
- request 中的 ip_hmac 和 fingerprint_hmac 在 35 天后置空；
- visitor 的 fingerprint_hmac 超过 35 天未重新观察时置空；
- 不保存原始 IP、原始 fingerprint 字段、提示词、模型完整 raw response 或 signed URL。

保留规则是产品技术契约，不构成任何部署地区的法律合规结论。

~~~

## 8. 建议初始限额

所有值必须配置化。建议一个月试运营的初始值为：

| 约束 | 初值 |
| --- | ---: |
| 单文件字节 | 小于 500,000,000 |
| 单任务媒体时长 | 小于 60 分钟 |
| visitor 每小时用户运行 | 5 |
| visitor 每日用户运行 | 20 |
| visitor 每日音频 | 240 分钟 |
| IP 每小时用户运行 | 15 |
| IP 每日用户运行 | 50 |
| visitor concurrency | 2 |
| IP concurrency | 4 |
| global concurrency | 20 |
| global daily cost | 部署配置，首日建议人民币 100 元 |

Trial 的 60 分钟边界比 Core 当前五小时边界更严格，但不修改 Core 常量。

不设置任务队列。visitor/IP 限额返回 429；全局并发、预算、磁盘或 readiness 拒绝返回
503。已经运行的任务不因新任务准入失败而强杀。

检查与接受必须位于同一个 TrialStore 写事务中，避免并发请求同时看到相同余额或槽位。

## 9. Execution、concurrency 与 budget 独立

execution_status、concurrency_active、budget_active 和 cost_status 是四个不同概念。
不能用一个 running 状态同时决定并发与预算。

不要求保存 concurrency_active 或 budget_active 布尔值。推荐派生：

~~~
concurrency_active =
  request 被执行器确认占用，且尚未被 stale sweep 回收

budget_active =
  budget_released_at IS NULL
~~~

### 9.1 Worker 存活

Worker 在执行期间每 30 至 60 秒更新 last_alive_at。媒体准备、ASR、纠错、GLM 和 ATA
长轮询都必须更新；它表示 Worker 仍被确认存活，不要求出现新的业务结果。

~~~
TRIAL_STALE_REQUEST_SECONDS = 14400
TRIAL_STALE_SWEEP_SECONDS = 300
TRIAL_UNKNOWN_BUDGET_HOLD_SECONDS = 86400
~~~

四小时只是默认值。TRIAL_STALE_REQUEST_SECONDS 必须大于当前所有合法单任务执行路径的
预期最长静默时间。Provider timeout、轮询方式或流水线阶段调整时必须同步复核。

### 9.2 周期 stale sweep

Trial 应用 lifespan 启动一个单主机轻量 sweep：

~~~
每 TRIAL_STALE_SWEEP_SECONDS
扫描 execution_status = running
且 last_alive_at < now - TRIAL_STALE_REQUEST_SECONDS
~~~

命中时以 compare-and-set 原子转为 interrupted、写 interrupted_at，并释放 visitor、
IP 和 global concurrency slot。启动恢复与新任务准入前也执行同一幂等回收，但不能只依赖
有人提交新任务才触发。

stale 回收不修改 budget_released_at，因此不释放预算占用。

### 9.3 Provider invocation 前执行栅栏

每次准备创建新的 Provider invocation 前必须调用等价于下列接口的执行栅栏：

~~~
TrialExecutionGate.assert_before_invocation(
    request_id,
    core_run_id,
    operation,
)
~~~

检查发生在 invocation 创建和发送之前。如果 request 已被 sweep 标记为 interrupted：

- 不得创建或发送新的收费 invocation；
- 不得把 request 静默恢复为 running；
- 已发送的 invocation 不强杀；
- 已在途调用可以持久化最终 receipt、usage、错误和成本；
- Worker 完成必要的幂等本地收尾后停止，不继续下一个 Provider 阶段；
- 后续恢复必须由明确的用户 resume 或系统恢复入口重新准入。

该栅栏只控制是否允许开始新的远端调用，不改变 Core invocation 状态、retry ancestry、
Artifact 内容或 Provider delivery_ambiguous 语义。

栅栏通过时，在同一 TrialStore 写事务中递增 `provider_invocation_count` 并刷新
`last_alive_at`；栅栏拒绝不递增。随后若 Registry invocation 创建或 usage snapshot 前发生
进程崩溃，数量差会让成本保持 pending，不能误记为零。拒绝通过专用
`TrialExecutionStopped` 传播：Core Run 收敛为 interrupted，Trial request 保持 interrupted
并记 `operationally_stopped`，且不进入成功率分母。没有任何 invocation 获准时费用为
not_incurred。

## 10. Budget occupancy

请求通过准入时：

~~~
estimated_max_cost_micros 已冻结
budget_released_at = null
cost_status = pending
~~~

预算占用只在费用已经确认，或未知等待期结束时释放：

| 情况 | concurrency | budget occupancy |
| --- | --- | --- |
| 正常运行 | 占用 | 保留 estimated_max_cost |
| stale 后 interrupted | 释放 | 继续保留 |
| 执行终态且费用完整 | 释放 | 释放，改计 calculated cost |
| 执行终态但费用待确认 | 释放 | 继续保留 |
| 失联 24 小时仍无法确认 | 已释放 | 标记 unknown 后释放 |

当所有 invocation 已计算或明确 definitely_not_sent：

~~~
cost_status = calculated 或 not_incurred
budget_released_at = now
~~~

当执行已结束但仍有在途调用、delivery_ambiguous、usage snapshot 待同步或必要 usage 缺失时，
预算继续占用。

失联超过 24 小时仍不能确认时：

~~~
cost_status = unknown
calculated_cost_micros = null
estimated_unknown_cost_micros = estimated_max_cost_micros
budget_released_at = now
~~~

因此成本保护和报表必须分别显示：

~~~
calculated_daily_cost
active_budget_occupancy
estimated_unknown_cost
~~~

准入时的实时公式为：

~~~
calculated_daily_cost
+ active_budget_occupancy
+ 当时已经形成的 estimated_unknown_cost
+ new_request_estimated_max_cost
<= effective_daily_budget
~~~

### 10.1 Unknown 成本的时间语义

estimated_unknown_cost 是事后分类，不是实时 actual。

例如 9 月 13 日创建的请求在 9 月 14 日达到 24 小时未知期限：

~~~
accounting_date = 2026-09-13
estimated_unknown_cost = 1.20 CNY
classified_at = 2026-09-14
quality = retrospective_estimate
~~~

历史报表可以把这 1.20 元归属到 9 月 13 日，但必须单列并显示它是 9 月 14 日才形成的
事后估算。不得把历史报表重述为“9 月 13 日准入时已经知道 1.20 元实际成本”，也不得把
它混入 actual/calculated cost。

在转为 unknown 前，该请求曾以 active_budget_occupancy 的形式实时占用预算；转为 unknown
后只是从活动占位重分类为事后未知估算。两者不得在同一时刻重复相加。

## 11. Provider usage 与成本

每个 Registry operation 必须具有显式分类：

| operation | 成本分类 |
| --- | --- |
| media_upload | non_billable_api；OSS 基础设施成本不进入 Provider API 成本 |
| qwen_asr | 按已验证价格规则使用 provider usage 或媒体时长 |
| doubao_asr | duration_derived |
| glm_selection | provider_actual token usage |
| qwen_correction | provider_actual token usage |
| kimi_correction | provider_actual token usage |
| ata | duration_derived 或该服务正式计费单位 |

覆盖测试必须与 Registry operation CHECK 集合同步。新增 operation 未指定 billable、
non_billable 或 unknown 策略时测试失败。

费用状态：

~~~
definitely_not_sent
-> cost_status = not_incurred
-> calculated_cost = 0

succeeded + 完整计费数据
-> cost_status = calculated

失败但完整 usage 已返回
-> cost_status = calculated

delivery_ambiguous / 必要 usage 缺失
-> cost_status = unknown 或 pending
-> calculated_cost = null
~~~

unknown 永不按零统计。

价格使用仓库内版本化 JSON，不建价格数据库。每个版本至少固定：

~~~
pricing_version
effective_at
provider
operation
resolved_model
billing_unit
rates
currency
~~~

价格更新新增版本，不回算历史。后台的“今日花费”必须标为“今日已计算 API 成本”；
它是实际 usage 或时长乘版本化价格得到的计算值，不宣称等于 Provider 最终发票。

## 12. Retry、resume 与恢复

| 行为 | 用户 job quota | Provider usage/cost |
| --- | ---: | ---: |
| 初次提交 | +1 | 正常记录 |
| 用户主动 retry | +1 | 正常记录 |
| 用户主动 resume | +1 | 正常记录 |
| 系统恢复原任务 | +0 | 新 invocation 正常记录 |
| Pipeline 内部 provider retry | +0 | 每个 invocation 独立记录 |

用户 retry/resume 产生新的 trial_requests 行并共享 job_id。系统恢复不伪造用户动作。
Provider retry 不增加 user-facing job 数，但其独立 invocation、usage 和成本全部保留。

失败或 interrupted Workspace 最多保留 24 小时。只有 Workspace 仍存在时才能 retry/resume；
超过期限后需要重新上传创建新 job。

## 13. OSS 与 Workspace 生命周期

### 13.1 OSS 前缀

~~~
trial/source/*
原始上传媒体
-> 7 天自动删除

trial/work/*
标准 WAV、Reference、终态快照和中间远端对象
-> 7 天自动删除

trial/result/*
final.srt 和必要的小型 result.json
-> 无自动删除规则
~~~

“长期保存”定义为 v0.6.2 不设置自动删除规则，不代表人为删除 bucket 后仍可恢复。
完整 Provider raw、ATA raw、Registry、音视频和大中间产物不得进入长期 result 前缀。

### 13.2 部署 readiness

Trial 部署必须配置 MediaObjectStore，并验证：

- source/work 生命周期规则存在、启用且不长于七天；
- result 前缀不被任何宽泛过期规则覆盖；
- 凭据具备所需 PUT、HEAD 和 presign 权限；
- 必要 bucket、region、endpoint 与前缀配置完整。

未通过时不接受任务。启动时必检，运行中每日只读复检；失败只暂停新任务，不强杀正在
运行的任务。

当前 Core 使用一个 MediaObjectStore factory 同时处理工作媒体和最终结果。实现时允许对
ProviderFactories 增加可选 result_media factory，默认仍回退到 media，以保持现有调用兼容；
Trial 注入不同前缀。MediaObjectStore Protocol 本身不增加生命周期或 GC 方法。

### 13.3 本地 Workspace

~~~
succeeded
-> result receipt 和 TrialStore result ref 持久化
-> usage snapshot 成功或进入有界 pending
-> 立即清理

failed / cancelled / interrupted
-> 最多保留 24h
-> 周期 stale workspace sweep
~~~

TRIAL_WORK_ROOT 的新任务准入使用双条件：

~~~
disk_used_ratio < 85%
AND
free_bytes >= (
  remaining_possible_concurrency
  * 500_000_000
  * TRIAL_WORKSPACE_EXPANSION_FACTOR
  + TRIAL_DISK_SAFETY_MARGIN_BYTES
)
~~~

默认 expansion factor 为 3；任一条件不满足，或无法读取磁盘容量，均 fail closed。并发上限
本身不随磁盘动态变化，运行中的任务也不因水位检查被强杀。

usage snapshot 失败最多重试 24 小时；期限后标记 unknown 并清理，不能为了统计失败永久占用
磁盘。

## 14. 长期历史与结果下载

最终结果长期保存：

- final.srt；
- 必要的小型 result.json。

不因 signed URL 过期而重新运行任务。

~~~
GET /trial/jobs/job_id/result
-> 验证 visitor Cookie 和 job 归属
-> 对精确 bucket/key/version_id 生成 10 分钟 signed URL
-> 302
~~~

302 必须包含：

~~~
Cache-Control: no-store
~~~

未归属、对象不存在或记录不存在统一返回 404。不允许 bucket listing，不把 signed URL 写入
TrialStore、长期页面缓存或任务历史。URL 过期后用户再次点击即可重新签发。

visitor、历史 job 索引和 result object ref 必须与长期结果共同保留，否则会形成存在但无法
访问的对象。清除 Cookie 后不提供历史恢复。

## 15. Heartbeat 与统计

浏览器每 60 秒调用 heartbeat。只更新 trial_visitors.last_seen_at，不保存 heartbeat 事件流。

~~~
online_now =
最近 5 分钟有 heartbeat 的唯一 visitor Cookie 数
~~~

“历史在线人数”拆成累计 Cookie UV 和历史峰值在线，不描述成真实自然人数。

后台至少展示：

- online_now、今日 Cookie UV、累计 Cookie UV、peak_online；
- 今日新 job、今日用户运行次数、今日音频分钟数；
- 成功率、失败率、interrupted 数、各拒绝原因；
- 平均、P50、P95 处理时间；
- 今日回访访客、跨日第二次使用率；
- 今日已计算 API 成本；
- active budget occupancy；
- estimated unknown cost；
- 成本覆盖率和 unknown 请求数；
- 平均每 job、每音频分钟成本；
- P50、P95 单 job 成本。

成本分位数和平均值只使用 calculated 样本，同时显示 coverage；unknown 不作为零样本。

## 16. Operator

后台只使用一个部署注入的 operator bearer secret，并使用 constant-time comparison。
不接入 AccountStore，不做 operator 注册或 RBAC。

操作员可：

- 暂停接受新任务；
- 恢复服务；
- 设置或清除当日预算覆盖。

每次控制修改必须追加 trial_control revision，保存 old_value、new_value、timestamp 和非空
reason。不得删除或改写历史控制记录。

预算耗尽或 material estimate overrun 可以自动追加系统控制 revision 并暂停新任务；
恢复必须由 operator 显式执行。

## 17. 威胁模型

本版防御：

- 普通用户重复点击；
- 单 Cookie、单 IP 高频提交；
- 删除 Cookie 但不换 IP 的低复杂度规避；
- 异常并发和明显超量任务；
- Worker 崩溃导致的并发槽位泄漏；
- 基础磁盘和成本事故。

本版不防御：

- 代理池和分布式攻击；
- 同时轮换 Cookie、IP 和浏览器环境；
- 专业自动化反检测；
- Cookie 被复制后的匿名历史访问。

最终兜底为 global concurrency、active budget occupancy、daily cost ceiling 和 operator
kill switch。该上限不是数学意义上的绝对账单封顶；在途 invocation 和 unknown 成本仍可能
形成尾部费用。

## 18. 验收标准

设计实现后至少验证：

1. Trial 路由不暴露或调用 Account/Auth；
2. Cookie、IP 和 fingerprint 原始值不落库；
3. 配额检查与接受原子；
4. 周期 sweep 在无新请求时也能回收 stale concurrency slot；
5. stale interrupted 不释放 budget occupancy；
6. interrupted request 不能开始新的 Provider invocation；
7. 在途 invocation 可以记录最终 usage/cost；
8. 24 小时 unknown 释放活动占位但保留 retrospective estimate；
9. historical report 不把 estimated_unknown_cost 描述成当时已知 actual；
10. 所有 Registry operation 都有成本分类；
11. usage 缺失不按零；
12. source/work 生命周期和 result 长期前缀通过 readiness；
13. 成功结果持久化确认前不删除 Workspace；
14. result 下载校验 Cookie 归属、精确 version，并返回 no-store 302；
15. peak_online 更新不产生 trial_control revision；
16. operator 预算覆盖保存 old/new/time/reason；
17. 磁盘使用率与峰值临时空间双条件、以及容量读取失败都会拒绝新任务；
18. 现有 v0.6.1 认证和 v0.5.4 字幕链回归测试不变。

Trial Web 依赖通过 `cueflow[trial]` optional extra 安装；`uvicorn` 与
`python-multipart` 不进入 Core 基础依赖。未安装 extra 时 `cueflow-trial serve` 必须给出明确
安装提示。`src/cueflow/static/trial/*` 同时进入 setuptools package-data 和 sdist manifest，
并以 packaged-resource 测试验证安装后可读。

## 19. 实施分段

运行时代码按以下层次实施和验证：

1. TrialStore schema、事务和统计；
2. Trial HTTP、Cookie、IP/fingerprint HMAC 与 operator；
3. Workspace ownership、周期 sweep 和 invocation execution gate；
4. 对象前缀、生命周期 readiness、长期结果和下载签名；
5. usage snapshot、版本化价格、预算占用与报表；
6. 完整失败路径和现有 Core 回归验证。
