# CueFlow v0.6.1 — Phone + Password Authentication 冻结设计

## 1. 目标

v0.6.1 把 v0.6.0 Account Core 扩展为完整的手机号账户系统：手机号是每个账户必须具有的
登录身份，密码与短信验证码是证明手机号控制权的两种认证方法。内部不可变 `user_id` 仍是
数据库主键；手机号不是 User 主键，也不能代替 `user_id` 参与内部关联。

一个可提交、可打开、可创建 Session 的正式账户必须同时具有：

```text
User
+ exactly one active phone AuthIdentity
+ exactly one Password Credential
+ linked Phone Reputation
```

系统禁止稳定落成 `User + Phone`、但缺少密码或 Phone Reputation 的半账户。

## 2. 本版范围

实现：

- 规范 E.164 手机号输入；
- 短信 challenge、验证、限流及短期安全事件；
- “手机号继续”统一注册/验证码登录；
- 首次注册强制设置密码；
- 手机号+密码登录；
- 修改密码、忘记密码与短信重置；
- 已登录+当前密码+新手机号短信验证的原子换绑；
- Access/Refresh token、rotation、reuse、当前设备和全部设备退出；
- 最多 5 个 active Session Family、30 天滑动 Refresh 和 180 天 Family 绝对上限；
- 长期 Phone Reputation、qualifying ban、block/unblock、overturn 和号码 reassignment；
- ASGI Auth HTTP、Cookie、Origin、CSRF 和公开错误映射；
- 专用的 qualifying-ban suspended account 短信验证删除流程。

不实现：微信、QQ、Apple、邮箱登录，2FA，Passkey，公网申诉 UI，管理员 UI/RBAC，支付，
真实短信厂商适配器或 ASGI Server 进程。CueFlow 提供 `SmsProvider` 和 ASGI app，部署环境负责
注入短信实现与 Uvicorn/Hypercorn 等服务器。

## 3. 账户、身份与凭据

`AuthIdentity` 表示“是谁”，`password_credentials` 表示“如何证明”。密码不是
`AuthIdentity.provider`。手机号 identity 通过 `phone_reputation_id` 外键连接长期 Phone
Reputation；该外键从 account-owned child 指向长期 ledger，使用 `ON DELETE RESTRICT`，删除
账户只能删除 child，绝不能向 reputation 反向级联。

`provision_user_with_phone()` 从生产 API 删除。正式生产源码没有绕过 AuthService 直接创建 User
的入口。测试使用仅位于 `tests/` 的 `make_test_account()` 建立合法前置状态；只有注册专项测试
才执行完整 SMS 注册流程。

## 4. Migration 002

Migration 001 的 SQL payload 和 checksum 保持冻结。Migration 002 给 `Migration` 增加可选 Python
`guard(connection)`；guard 不进入 SQL checksum，checksum 仍只证明规范 SQL payload 未漂移。

执行顺序：

```text
acquire OS migration lock
→ read v1 ledger
→ create and integrity-check v1 backup
→ BEGIN EXCLUSIVE
→ re-read ledger and verify SQL checksum
→ run Migration 002 guard
→ execute the first Migration 002 SQL statement
→ append ledger v2
→ exact schema/invariant/FK validation
→ COMMIT
```

guard 检查以下全部 v1 account-owned 表：

```text
users
auth_identities
session_families
sessions
account_audit_events
```

任意一张非空即拒绝：

```text
nonempty v1 development Account database is unsupported;
delete and recreate it explicitly;
a pre-migration backup was left at <absolute backup path>
```

拒绝时事务回滚，不执行任何 Migration 002 schema statement，源数据库的 schema、数据和 ledger
保持不变；已验证的备份保留。失败的 pre-release migration backup 是开发者管理的文件，在确认
源库完整后可人工删除；程序不自动清理。Migration 002 不回填、不生成随机密码，也不自动删除
开发库。空 v1 或全新 `0 → 1 → 2` 才能升级。

## 5. Schema 生命周期

`ACCOUNT_OWNED_TABLES` 随 User 删除：

```text
users
auth_identities
password_credentials
session_families
sessions
access_tokens
account_qualifying_bans
account_audit_events
```

`AUTH_TRANSIENT_TABLES` 按 TTL 或操作状态清理，不属于账户业务本体：

```text
sms_challenges
phone_verification_grants
auth_rate_limit_buckets
auth_security_events
```

`PHONE_REPUTATION_TABLES` 长期保留，固定为五张：

```text
phone_reputations
phone_reputation_operations
phone_reputation_event_log
phone_sanction_events
phone_status_events
```

`sms_challenges.user_id` 与 grant 的 `user_id` 均可为空；注册时尚不存在 User，换绑和账户删除
则绑定当前 User。User 删除使用 `ON DELETE SET NULL`，短期反滥用状态可继续保留至 TTL。

## 6. 注册与手机号继续

### 6.1 请求验证码

```text
phone → strict E.164 validation
→ phone/client/IP rate limit
→ Phone Reputation check
→ blocked: do not send, return phone_blocked
→ create pending challenge
→ call SmsProvider
→ success: challenge=sent
→ definite provider failure: challenge=failed, return temporary unavailable
```

短信 purpose 固定为：`phone_continue`、`password_reset`、`phone_change`、
`account_erasure`、`phone_appeal`。后两种允许 blocked phone 请求，但仍受限流。

### 6.2 验证验证码

验证码只保存 HMAC，不保存明文。challenge 绑定 phone key、purpose、有效期和最多 5 次验证尝试。

```text
verify phone control
├─ phone_continue + existing User
│  → verify User active, Password present, Phone normal
│  → create complete login state
└─ no User / another purpose
   → issue one-time phone verification grant
```

### 6.3 Registration grant

`K_phone_auth` 与 `K_grant` 分离。规范手机号先计算短期 phone key。grant HMAC 使用带版本、domain
separation 和长度前缀的规范字段，绑定：raw grant、grant id、phone key、purpose 和 expiry。

grant 一次性、有 TTL、不能跨手机号、不能跨 purpose。短期 phone key 和 grant key 保存
`key_id`，在 TTL 内允许验证 keyring 中仍保留的旧 key。

### 6.4 最终注册事务

密码策略检查与 Argon2id hash 在事务外完成。最终事务内再次验证 grant、手机号绑定、手机号
未占用和 Phone Reputation 未 blocked，然后原子完成：

```text
BEGIN IMMEDIATE
→ create User
→ create or reuse long-lived Phone Reputation
→ create linked active Phone Identity
→ create Password Credential
→ create Session Family
→ create Session
→ create Access Token digest
→ consume registration grant
→ write Account Audit
COMMIT
```

任一步失败全部回滚。raw Access/Refresh/CSRF token 在事务前后只存在内存中，数据库只保存 HMAC
digest。客户端收到成功响应即表示注册已提交；若响应丢失，重试旧 grant 不会创建第二个账户。

取消注册会删除未消费 grant 与其 challenge；客户端消失时由 TTL cleanup 删除。最终事务前没有
User，因此取消等价于“没有来过”。

## 7. 密码

直接依赖 `argon2-cffi`，保存标准 Argon2id PHC 字符串。0.6.1 不使用 pepper，也不预留
`pepper_key_id`。生产初始参数：

```text
memory_cost = 65536 KiB
time_cost = 3
parallelism = 4
salt_len = 16 bytes
hash_len = 32 bytes
```

密码 NFC 规范化后要求 15–128 Unicode codepoints；不要求大小写、数字或特殊字符组合，不限制
正常特殊字符。`PasswordBlocklist` 使用本地、可测试的数据源，不把在线 HIBP 可用性耦合进
注册。0.6.1 内置 blocklist 只有 3 条机制验证用 seed 数据，不是完整的 NIST
compromised-password blocklist，也不代表生产级泄露密码数据覆盖；面向更大规模生产用户前必须
接入有来源、版本、更新时间和条目数量的正式离线数据集。原始密码永不进入数据库、日志、错误
或 audit。

`PasswordHashService` 显式注入。生产默认只能使用生产参数；测试低成本参数只能通过构造参数
显式传入，没有环境变量开关。登录成功时若 PHC 参数需要升级，透明 rehash。

## 8. 密码与手机号变更

密码登录先公开检查 phone blocked，然后统一返回 `phone or password is incorrect`，不区分 User
不存在、密码错误或账户 suspended；不存在的账户仍执行一次 dummy Argon2 verify，避免明显的
“是否注册”计算量旁路。失败按 phone/client/IP 渐进 cooldown，不做永久锁号。

已登录修改密码必须提供有效 Access token、当前密码和新密码；成功后以 `password_changed`
撤销全部旧 Family/Session/Access token，并为当前设备创建全新登录状态。

忘记密码通过 `password_reset` SMS grant 更新 hash，以 `password_reset` 撤销全部登录状态，
不会自动登录。

自助换绑必须提供有效 Access token、当前密码和新手机号 SMS grant。新手机号已被绑定时明确
返回 `phone_already_registered`。事务中创建或复用新 Phone Reputation、旧 phone detached、
新 phone active，并以 `phone_changed` 撤销全部旧登录状态、签发新的当前设备登录状态。任何
时刻都不存在 `phone → NULL`。

## 9. Session 与 token

Access token 15 分钟；Refresh token 每次 rotation 产生新的 30 天有效 leaf。Session Family
绝对期限只由 `family.created_at + 180 days` 计算，不增加冗余字段。

代码中只有一个权威 Session 有效性函数和一个 180 天常量来源；Account Core、Auth refresh、
Access token 认证和 active-family eviction 不得各自复制判断或提供测试专用 TTL 配置。边界测试
通过调整 `family.created_at` 覆盖第 179 天仍有效、第 180 天失效。

统一有效性：

```text
User.status = active
AND linked Phone Reputation.status = normal
AND Family not revoked
AND now < Family.created_at + 180d
AND Session not revoked/replaced
AND now < Session.expires_at
AND Access token not revoked/expired（访问请求）
```

Refresh reuse 撤销整个 Family 并写短期 `token_reuse` 安全事件。Family 到 180 天边界必须重新
认证；rotation 和 active-family 计数使用同一边界。最多 5 个 active Family，第六个原子淘汰
最老 Family。

Session revocation reason 固定为九个，Python 集合必须与 SQLite CHECK 完全一致：

```text
user_request
refresh_token_reuse
user_suspended
session_limit_eviction
administrative_revoke
logout_all
password_changed
password_reset
phone_changed
```

## 10. Phone Reputation 密钥与隐私

`K_phone_auth` 用于 challenge、限流等短期状态，可正常轮换。`K_phone_reputation` 是长期稳定
假名化 lookup key，不做常规定期轮换；紧急轮换必须执行显式全量数据迁移。Phone encryption
使用独立 AES-256-GCM keyring。

每条 reputation 存储：

- 稳定 `phone_reputation_id`；
- `HMAC(K_phone_reputation, canonical E.164)` 及 key id；
- AEAD 加密 E.164、encryption key id、独立 96-bit CSPRNG nonce；
- 当前 generation、count/status 投影和时间。

AEAD AAD 精确为：

```text
UTF8("cueflow:phone-reputation:v1:") || ASCII(phone_reputation_id)
```

同一个 encryption key 下 nonce 受数据库唯一约束。未知 key id、解密失败、AAD/tag 失败或解密
手机号与稳定 HMAC 不匹配均 fail closed，不能解释为“没有 reputation”。AEAD 不检测整行删除，
文档和实现不作此声明。

账户注销不会删除独立手机号级长期记录。手机号以可重新关联的稳定假名标识和 AEAD 密文保留，
不是匿名数据。隐私说明必须明确：账户、认证、Session 和账户 audit 被删除；Phone Reputation
及处罚历史因跨账户反滥用、封禁执行和号码重新分配纠错而长期保留。

## 11. 双事件流和投影

`phone_reputation_event_log` 是唯一顺序权威：

```sql
UNIQUE(phone_reputation_id, generation, sequence_no)
UNIQUE(operation_id, operation_stream_slot)
```

`operation_stream_slot` 固定 `1=sanction/count`、`2=status`。每个 generation 从 sequence 1
重新开始：sequence 1 是 status `generation_started → normal`，sequence 2 是 sanction
`generation_started, delta=0`。上一条事件永远只指同一 reputation、同一 generation。

每个 head 恰有一个与 `stream_type` 对应的 detail；每个 detail 必须有 head。事务写入保证正常
路径，deep validator 双向验证损坏。一次 operation 可同时产生 count 和 status 事件；重试必须
按 operation header、request fingerprint、两个 expected stream count 和固定 slot 验证整体完整，
不能只查其中一张 detail 表。

qualifying ban 使同一个 User 最多贡献一次仍有效的处罚。相同 operation id 重试幂等；不同
operation 再次处罚同一 User 冲突。overturn 对同一 target 只能一次，并追加到原处罚所在
generation；正式 overturn 后该 User 未来可因新独立违规再次贡献一次。

达到第三次处罚时，count event 和 `phone_blocked` status event 在同一事务写入。已经 blocked
再次 admin block 返回 `already_blocked`，operation 记录保留但不写 `blocked→blocked` 垃圾事件。
blocked 状态下新的 qualifying ban 仍增加 count，但不重复 status event。

admin unblock 只改变 status，count 历史不清零；例如 `count=3,status=normal` 合法。下一次有效
ban 变为 4 并再次 blocked。运营商号码重新分配执行显式操作：确认不存在 active identity，
`current_generation += 1`、新代 count=0/status=normal；旧代历史保留但不参与当前投影。

`phone_reputations` 是当前投影，count 与 status 分别由两个事件流证明，不从 count 单向推导
status。按手机号读取、登录、注册、处罚、申诉、换代时执行该手机号的完整解密和事件重放。
AccountStore 启动只验证 schema、FK、索引和 User 的快速结构 invariant，不全量解密百万手机号；
全量 deep validation 由 maintenance API/命令显式执行。

`PhoneReputationService` 构造时自动执行 keyring preflight，上层 HTTP、CLI 或 Worker 不负责也
不能忘记调用。共享同一 `PhoneReputationCrypto` 的 request-scoped services 对同一数据库文件在
单进程内只扫描一次数据库 key ids；未知稳定 lookup key 或 encryption key 均 fail closed。
`find_by_phone()` 仅用 current/compatible stable keys 做精确索引查询，不扫描全表；跨兼容 key
命中多条 reputation 表示同一手机号存在重复长期身份，必须 fail closed。

进程级 preflight 缓存不能保护新旧进程并存的密钥轮换窗口。因此 `ensure_phone_tx()` 只有在
known-key 精确查询没有命中、即将创建新 reputation 时，才在当前 `BEGIN IMMEDIATE` 写事务中
强制执行一次不使用缓存的数据库 key-id 检查，然后按 known keys 再确认一次不存在，最后才允许
INSERT。任意未知 lookup/encryption key 都使整个创建或注册事务 fail closed；普通查询不承担这次
全表检查。

单手机号 deep validation 一次批量读取该 reputation 的 operation、head、sanction detail 和
status detail，再在内存中校验配对及重放，复杂度为 O(该手机号自己的历史事件)，而不是
O(全体手机号)。当前预期单手机号事件数量较小；只有未来单号码历史显著增长时，才评估 projection
cache 或周期性全量验证，不在 0.6.1 提前引入。

## 12. Account 与 Phone 状态

两个状态维度彼此独立：

```text
Account: active | suspended
Phone Reputation: normal | blocked
```

有效认证要求 `Account active AND Phone normal AND credential valid`。手机号 blocked 时即使 User
仍为 active，也立即拒绝认证并撤销现有 Session；unblock 不会复活旧 Session。公开手机号入口
明确返回 HTTP 403 `phone_blocked`，接受该业务状态可枚举，并提供联系客服/申诉指引。

qualifying ban 会 suspend 当前 User；普通 suspended User 仍不能自助注销。携带有效 qualifying
ban 的 suspended User 可通过专用 `account_erasure` SMS 验证删除账户。删除桥接表不会删除其
引用的长期 sanction event。

## 13. HTTP 冻结契约

CueFlow 提供 Starlette ASGI app，不把 Uvicorn 加入运行依赖。`starlette<1` 是有意的兼容性
上界；未来升级 Starlette major version 或 httpx 2.x 时必须重新运行 Auth HTTP compatibility
tests。浏览器认证使用：

```text
__Host-cueflow-access
__Host-cueflow-refresh
Secure; HttpOnly; SameSite=Strict; Path=/
```

所有 Auth POST 都校验受信 Origin；操作现有浏览器 Session 的请求还必须通过 double-submit
CSRF cookie/header，并校验该 CSRF 值与 Access token 数据库记录的绑定。Refresh 时 Access
credential 可以已经超过 15 分钟认证 TTL，但浏览器仍保留其 cookie 作为 CSRF 绑定材料；它
不能再用来完成普通认证。Access/Refresh token 不进入 Web Storage。基础公开语义：

```text
202  verification code request accepted
401  authentication_failed
403  phone_blocked / csrf_failed / origin_not_allowed
409  phone_already_registered or state conflict
429  rate_limited + Retry-After
503  sms_provider_unavailable / reputation integrity unavailable
```

密码公开错误不泄露手机号是否注册；已登录并完成 step-up 的换绑允许明确返回手机号已占用。
所有 Auth 响应携带 `Cache-Control: no-store`。冻结路由集合为：

```text
POST /auth/phone/continue/request-code
POST /auth/phone/continue/verify-code
POST /auth/registration/complete
POST /auth/registration/cancel
POST /auth/password/login
POST /auth/password/reset/request-code
POST /auth/password/reset/verify-code
POST /auth/password/reset/complete
POST /auth/password/change
POST /auth/phone/change/request-code
POST /auth/phone/change/verify-code
POST /auth/phone/change/complete
POST /auth/session/refresh
POST /auth/session/logout
POST /auth/session/logout-all
POST /auth/account/erasure/request-code
POST /auth/account/erasure/verify-code
POST /auth/account/erasure/complete
```

`create_auth_app()` 接受 request-scoped `AuthService` factory；每次请求独占并关闭自己的
`AccountStore`/SQLite connection，ASGI worker 不共享同一 connection。反向代理提供真实 client
address，CueFlow 不直接信任未经部署层校验的 forwarded-IP header。

## 14. 发布门槛

普通单元测试使用显式 fast Argon2；少量专项测试使用真实生产参数验证 hash/verify/rehash。
`benchmarks/argon2_concurrency.py` 在目标部署机器运行真实并发 benchmark，必须由部署方给出并
满足 p95/资源阈值后才能 tag/release v0.6.1。当前开发机测量不能替代目标环境 gate。

发布前必须通过：定向与全量 pytest、Ruff、strict MyPy、build、隔离 wheel install/import、
SQL checksum、Migration guard 四项验收、schema/reason parity、生产源码 provision 绕过搜索、
Argon2 目标机器 benchmark。
