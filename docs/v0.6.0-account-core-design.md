# CueFlow 0.6.0 — Account Core 冻结设计

## 目标与边界

0.6.0 只建立可持久、可演进的账户状态核心。一个 `User` 是唯一账户主体，可以绑定多个
`AuthIdentity`；身份不是用户，不因登录渠道不同而创建重复账户。

本版不实现 `login()`、`register()`、短信或邮件验证码、OAuth callback、微信/QQ/Apple
登录、HTTP endpoint、权限、支付或 UI。未来 Auth 层负责证明请求者控制某个身份，再把
`VerifiedIdentityClaim` 交给 Account Core；Core 不发送验证码，也不验证第三方凭证。

`users.profile` 不在 0.6.0 schema 中。昵称、头像、locale 等有明确需求后再以受约束字段加入；
手机号、邮箱、OAuth subject、token 或 secret 不得绕过正式表进入自由 JSON。

## 生命周期和存放位置

Account 数据库与 Workspace Registry 是两个生命周期：

```text
CueFlow Server
├─ explicitly configured account.sqlite3
├─ Workspace A/.cueflow/registry.sqlite3
└─ Workspace B/.cueflow/registry.sqlite3
```

上层必须向 `AccountStore(path: Path)` 注入绝对路径。Workspace 不创建、查找或拥有 Account
数据库。AccountStore 也不会把数据库放进 `<Workspace>/.cueflow/`。SQLite 是 0.6.0 的存储
实现；该边界允许未来服务器将 AccountStore 换成 PostgreSQL，而 Workspace Registry 继续使用
SQLite。

账户数据不可再生，因此 Account schema 不能沿用 Registry 的 current-only、不迁移策略。
Registry 15 和 Artifact 12.0.0 的拒绝旧版本规则保持不变，只适用于原有执行状态。

## 数据模型

所有时间均为 UTC Unix epoch milliseconds，使用 SQLite `INTEGER`。到期边界统一为
`now_ms >= expires_at`。

### users

| 字段 | 契约 |
| --- | --- |
| user_id | 不透明稳定 ID，主键 |
| status | `active` 或 `suspended` |
| created_at | 创建时间 |
| updated_at | 最后一次账户状态或身份变化时间 |

### auth_identities

| 字段 | 契约 |
| --- | --- |
| identity_id | 不透明稳定 ID，主键 |
| user_id | 所属 User |
| provider | `phone/email/wechat/qq/apple` |
| provider_subject | Provider 内的规范 subject；敏感字段 |
| status | `active` 或 `detached` |
| verification_method | 上游如何完成验证，不保存凭证 |
| verified_at / created_at | 验证和持久化时间 |
| detached_at | 历史身份解绑时间 |
| replaced_by_identity_id | 换绑链的后继身份 |

`(provider, provider_subject)` 在 active 身份中全局唯一。`phone.provider_subject` 只接受规范
E.164，例如 `+8613812345678`；国家/地区解析与输入 normalize 属于后续短信 Auth 层。

每个 User 的 active phone 必须恰好为 1。数据库唯一索引保证最多一个，AccountService 的原子
provision/replace、打开时 invariant 检查保证不能稳定落成零个。微信、QQ、Apple 和邮箱只是
附加身份，不能代替手机号。普通 API 没有 `detach_phone()`；正常和管理员恢复都执行
`old phone -> detached` 与 `new phone -> active` 的同一事务替换，不执行 `phone -> NULL`。

### session_families 与 sessions

一个长期登录设备对应一个 `session_family`，每次 refresh rotation 在该 family 内新增一个
`session`：

```text
Session A --replaced_by--> Session B --replaced_by--> Session C
```

Family 保存 `created_at/revoked_at/revocation_reason`。Session 保存
`created_at/expires_at/revoked_at/replaced_by_session_id` 和唯一 `refresh_token_hash`。
同一 family 同时最多一个未撤销、未替换的 leaf；只要 `replaced_by_session_id` 非空，数据库
CHECK 就要求该 Session 已经 revoked。

Refresh token 必须由 Auth 层使用至少 256-bit CSPRNG 生成。数据库只接受：

```text
hmac-sha256:<key_id>:<HMAC-SHA256(server_secret, raw_refresh_token)>
```

`key_id` 为未来密钥轮换保留。raw token 与 server secret 只属于未来 Auth/token 层；Account
Core 不提供 digest 计算 API、不持有 secret，只校验并持久化规范 digest。Core 的
`rotate_session()` 在一个事务内撤销旧 Session、创建新 Session、写入
`replaced_by_session_id` 并记录 audit。

`find_session_by_refresh_hash()` 是 raw lookup，可以返回 revoked、replaced、expired 或所属 User
已 suspended 的 Session，以便 Auth 层识别 reuse。`find_active_session_by_refresh_hash()`、
`session_is_active()` 与 `rotate_session()` 共同复用唯一有效性判据：

```text
revoked_at IS NULL
AND replaced_by_session_id IS NULL
AND now_ms < expires_at
AND user.status = active
```

Auth 层一旦判定 reuse，调用 `revoke_session_family(reason="refresh_token_reuse")`。每次调用都在
同一事务记录 `token_reuse_detected`；若 family 此前仍 active，再记录一次
`session_family_revoked`。已经 revoked 的 family 被重复攻击时继续新增 detected 事件，但不伪造
第二次状态撤销事件。

`MAX_ACTIVE_SESSION_FAMILIES = 5` 是 AccountService 产品策略，不写入 SQLite schema。创建第
6 个 active family 时，在同一事务内撤销最老的 active family、写
`session_family_evicted` audit，再创建新 family。若任何一步失败，旧 family 和新 family 的
变化全部回滚。这里的 active 指 family 未撤销且仍有未过期的 live leaf。

### account_audit_events

Audit 保存账户状态变化、身份绑定/换绑、Session 创建/rotation/revoke、family 淘汰等事件。
metadata 只保存稳定类别、原因码和数量，不保存手机号、邮箱、provider subject、raw token 或
secret。附加身份事件固定为 `identity_linked`。当前 append 是 AccountService 内部机制；
`list_audit_events()` 提供读取。

## 状态规则

- `active` User 可以换绑手机号、附加其他身份、创建/rotation Session，并可进入注销事务。
- `suspended` User 不能创建或 rotation Session，也不能自助注销；冻结时撤销其所有 family
  和 Session。
- `suspended -> active` 只恢复账户状态，任何旧 Session 都不会复活；需要创建新 Session。
- `revoke_session()`、`revoke_session_family()` 和 `revoke_all_sessions()` 是 Core 的事务机制；
  何时调用及异常登录/step-up 判断属于 Auth policy。
- `revoke_all_sessions()` 返回本次从未撤销变为撤销的 Session 数量。
- Session revocation reason 只允许 `user_request`、`refresh_token_reuse`、`user_suspended`、
  `session_limit_eviction`、`administrative_revoke`、`logout_all`；它们是机器 reason code，
  不是备注栏。管理员手机号替换单独只接受 `account_recovery`。

> **Superseded by v0.6.1:** 从 v0.6.1 起，因 qualifying account ban 而 suspended 的账户可走
> 专用短信验证账户删除流程。账户数据被删除，但手机号级 Phone Reputation 和 sanction
> history 长期保留。其他 suspended 账户仍不能自助注销。

## 注销语义

未来 UI/Auth 必须在调用 `erase_account()` 前完成不可恢复警告、二次确认和手机号重新验证。
Core 只接收已经授权的操作。只有 `active` User 可以自助注销；`suspended` User 必须走未来的
管理员或申诉流程。

`erase_account(user_id)` 在一个事务内按外键顺序删除以下全部 account-owned 数据：

1. `account_audit_events`
2. `sessions`
3. `session_families`
4. `auth_identities`
5. `users`

删除后 User 为 NotFound，旧 refresh token 永久无效，原手机号和其他身份可以被新 User 绑定。
不保留匿名墓碑、不保留可识别 audit、不创建注销专用备份。代码中的 account-owned table 集合
与擦除顺序必须完全相等；新增 Account 表而未登记擦除覆盖时失败关闭。
注销不调用普通 Session revoke API，也不使用 `account_erasure` reason；它就是一个独立的
destructive transaction。

> **Superseded by v0.6.1:** “不保留匿名墓碑”仅描述 account-owned 数据。v0.6.1 起每个正式
> 进入账户体系的手机号都有独立长期 Phone Reputation；账户注销不会删除其中的稳定假名标识、
> AEAD 加密 E.164 或手机号处罚事件。它们可由 CueFlow 持有的密钥重新关联，因此不是匿名数据。

注销不会打开并重写迁移或灾备产生的既有历史备份；这些备份按部署方既定保留周期淘汰。
因此在保留期内恢复注销前的旧备份可能重新出现已注销数据，部署方必须把恢复后的删除重放和
备份保留期纳入其数据治理。0.6.0 不声称“所有历史备份中立即物理消失”。

## Forward-only migration

`account_schema_migrations` ledger 是 Account schema 版本的唯一权威；AccountStore 不使用
`PRAGMA user_version` 作为第二份权威。每个已发布 migration 固定版本、名称、规范 SQL payload
和 SHA-256 checksum；发布后禁止修改，修复只能新增 migration。

Migration 001 在 v0.6.0 首次正式 tag/release 前仍属于 pre-release，可以随最终 schema 修订并
重新计算 checksum。v0.6.0 一旦正式发布，Migration 001 的 payload 与 checksum 永久冻结；之后
任何 schema 变化只能新增 migration。此前由开发版本创建的 Account DB 不在兼容承诺内：若
pre-release schema/checksum 已变化，删除该开发数据库并重新创建，不能伪装成生产迁移。

迁移流程：

```text
acquire account-specific OS lock
→ re-read migration ledger
→ for an existing schema, create and integrity-check SQLite backup
→ BEGIN EXCLUSIVE
→ apply each contiguous migration and append ledger row
→ validate exact schema, account invariants and foreign keys
→ COMMIT
→ release OS lock
```

任一步失败则 ROLLBACK，原数据库保留为旧版本，AccountStore 拒绝打开，等待修复后重新向前
迁移；不自动降级。空数据库执行初始 0 -> 1 时没有不可再生数据，因此不创建空库备份。
备份发生在 schema mutation 前，并由与 Account migration 独立的绝对目录承载。

OS lock 覆盖版本检查、备份和整个 migration chain，防止两个进程同时升级；SQLite
`BEGIN EXCLUSIVE` 保证数据库 mutation 原子性。该 lock 独立实现，不修改或抽取
`project.py:single_writer`。

## API 表面

0.6.0 暴露的机制包括：

- `migrate_account_database(...)`、`AccountStore(path)`；
- `provision_user_with_phone()`、`get_user()`、`set_user_status()`；
- `list_identities()`、`get_identity()`、`find_active_identity()`、`attach_identity()`、
  `replace_phone()`、`administrative_replace_phone()`；
- `create_session()`、`get_session()`、`find_session_by_refresh_hash()`、
  `find_active_session_by_refresh_hash()`、`session_is_active()`、`rotate_session()`、
  `revoke_session()`、`revoke_session_family()`、`revoke_all_sessions()`；
- `list_audit_events()`、`erase_account()`。

本版明确不暴露 `login/register/send_verification_code/verify_sms_code/oauth_callback` 或任一
Provider 专用登录入口。

错误类型以 `AccountError` 为根，区分 NotFound、账户状态错误、身份冲突、Session 状态错误、
迁移失败和迁移锁冲突。身份并发依赖 `BEGIN IMMEDIATE` 与唯一索引：两个独立 SQLite
connection 同时绑定同一 active identity 时，必须恰好一个成功。
嵌套 AccountStore 业务事务是调用方违反 API 契约，抛 `ContractError`，不归类为 migration
失败。两个 connection 并发创建第 5/第 6 个 family 时也由相同写事务串行化，最终不能超过 5。

## PII 安全边界

0.6.0 不提供手机号/邮箱/provider subject 的应用层字段加密。Account DB、迁移备份和灾备均为
敏感数据：不得公开，使用最小 OS/服务账户权限，不写普通日志、错误消息或 audit metadata，
并依赖部署环境的磁盘/云盘静态加密与进程权限隔离。未来若增加字段级加密，需要单独设计
密钥管理、轮换和可查询唯一索引，不能静默改变本契约。

## 产品版本与 Artifact 身份

`APP_VERSION = "0.6.0"` 只表示 CueFlow 产品版本。Artifact ID 不再直接读取产品版本；18 个
Artifact kind 各自通过 `ARTIFACT_PRODUCER_VERSIONS` 获取语义生产版本，并永久测试：

```python
assert set(ARTIFACT_PRODUCER_VERSIONS) == ARTIFACT_KINDS
```

0.6.0 初始的 18 个 producer version 全部保持 `0.5.4`，因为账户功能没有改变字幕 Artifact
语义。通过 `git archive 53d56c9` 得到的隔离旧源码，以固定 run_id、UUID、object_key 和所有
语义随机量，在两个独立 Python 进程及各自独立临时目录中重新生成了字节相同的
24-artifact/18-kind manifest；其 SHA-256 为
`6000CA674908A5BEB460FC3C16069C76FE9E32CBBD820761F8A22A3BB68A4805`。每条 golden 冻结
`artifact_kind/scope_key/artifact_id/content_hash/producer` 五个字段；当前代码也由两个独立进程
逐项比较。这个 fake object-store golden 只证明 0.5.4 -> 0.6.0 重构等价，不承诺生产环境跨
Run 的绝对 Artifact ID。

`COMPONENT_VERSION` 常量不再存在。Artifact envelope 的 `producer.component_version` 字段仍是
既有 Artifact Schema 12.0.0 的字段名，其值现在来自对应 artifact kind 的 producer version。
